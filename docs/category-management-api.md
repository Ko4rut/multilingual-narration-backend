# POI Category Management API

This feature extends the existing Catalog domain. **There is one canonical
`poi_category` table**, used by POI classifications and Offline Package scopes.

## REST contract

| Method | Path | Required RBAC action | Result |
|---|---|---|---|
| GET | `/api/v1/catalog/categories` | public | 200; unchanged list |
| GET | `/api/v1/admin/catalog/categories` | POI Management:read | 200; list |
| POST | `/api/v1/admin/catalog/categories` | POI Management:create | 201; category |
| PATCH | `/api/v1/admin/catalog/categories/{id}` | POI Management:update | 200; category |
| DELETE | `/api/v1/admin/catalog/categories/{id}` | POI Management:delete | 204; no body |

POST body: `{"category_name":"Art Museum","category_code":"art-museum"}`.
PATCH body: `{"category_name":"Fine Art Museum"}`. Category ID is generated by
the Backend as `cat-xxxxxxxx`. `category_code` is immutable after creation,
because released `offline_package.package_key` contains it.

Names are trimmed, not blank and at most 120 characters. New codes must be
lowercase alphanumeric with internal single hyphens, at most 30 characters.
Legacy seeded categories use uppercase codes (e.g. `MUSEUM`), which remain
valid existing data and are not silently renamed. New code conflicts are
checked case-insensitively to reject `museum` if `MUSEUM` already exists.

Bad input: 422. Duplicate category name/code: 409. Missing category on
PATCH/DELETE: 404. DELETE when any POI category mapping or offline package
references this category: 409. Unauthenticated requests: 401; insufficient
POI Management permission: 403.

## Safety

A new Alembic migration `0012_poi_category_constraints` follows the
`0011_offline_auto_build` revision on
`feature/offline-package-publish`. It enforces unique names, trimmed
nonempty names, format checks compatible with legacy seeded codes, and
converts the mapping-to-category foreign key from CASCADE to RESTRICT.
It **fails without changing old records** if existing data violates those
rules. Back up and review conflicts before applying the migration.

The service owns transactions; reads and mutations share one Session, and a
Category row is locked for rename/delete. Server rejects referenced deletes,
while DB RESTRICT provides a second guard. No automatic POI/category
mapping changes and no Offline Package reclassification are performed.

The Catalog seeder no longer rewrites category_name of existing seeded
categories, preserving Administrator edits.

## Deployment

1. Start from `feature/offline-package-publish` or a branch that includes
   migration 0011; never cherry-pick 0012 onto plain develop without
   reconciling Alembic ancestry.
2. With the intended database safely backed up, run `alembic upgrade head`.
3. Run the existing seeder only if needed for reference data.
4. Start Backend and use the Admin Web CRUD UI on
   `feature/poi-category-crud-ui`.

Verification should include: focused tests, `alembic check` and an
isolated PostgreSQL upgrade/downgrade and authenticated CRUD integration.
CI provisions a disposable PostgreSQL 16 service, runs Alembic upgrade/check,
and verifies Category CRUD persistence. Browser E2E with a real JWT/Admin session
remains a separate deployment check.
